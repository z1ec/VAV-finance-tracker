# ADR-0002: CI/CD — two images in GHCR, deploy over SSH with health check and rollback

- Status: accepted
- Date: 2026-11-12

## Context
Until stage 1 the tracker was deployed by hand (`git pull && docker compose up --build` on the
server), without CI, linters or a rollback path. The Momentum bot on the same server already uses
a proven pipeline (its ADR-0008). Building on the 1 GB server is slow and competes with the bot.

## Decision
- **Two images, one tag.** `ghcr.io/z1ec/finance-tracker-backend` (FastAPI, non-root uid 10001,
  Docker `HEALTHCHECK` on `/api/health`) and `ghcr.io/z1ec/finance-tracker-web` (Caddy +
  static frontend, Caddyfile validated at build time). Both are tagged `sha-<7>` and `latest`
  by the same workflow run, so a tag always names a consistent pair.
- **CI** (`ci.yml`, every push/PR): ruff, ruff format, mypy, pytest with coverage; actionlint,
  shellcheck, `deploy.sh` dry-run tests; build both images and smoke-test them (backend health
  200 with a random test `.env`, runs as uid 10001, refuses insecure secrets on a real domain;
  `caddy validate`).
- **CD** (`deploy.yml`): push to `main` → CI → build & push (platform from `vars.DEPLOY_PLATFORM`)
  → copy `deploy/docker-compose.prod.yml` and `deploy/deploy.sh` over SSH → `deploy.sh <tag>`.
  Runs only when `vars.DEPLOY_ENABLED == 'true'`. `workflow_dispatch` with `image_tag` redeploys
  an existing tag (rollback) without building.
- **deploy.sh** logs in to GHCR with the run's `GITHUB_TOKEN` read from stdin, pulls and starts
  both services, waits for backend `healthy` **and** `https://$DOMAIN/api/health` through Caddy
  (resolved to 127.0.0.1), records `.last_successful_tag` / `.previous_successful_tag`, otherwise
  rolls both services back to the last good tag and fails the job; keeps only the current and
  previous image tags; logs out on exit.
- **Access:** GitHub Environment `production` with `DEPLOY_HOST`, `DEPLOY_USER=deploy`,
  `DEPLOY_PORT`, `DEPLOY_SSH_KEY` (a key pair dedicated to this repository) and
  `DEPLOY_KNOWN_HOSTS` (pinned host key, `StrictHostKeyChecking=yes`);
  `concurrency: deploy-production`.

## Alternatives
- **One image with Caddy + uvicorn** — simpler tagging, but mixes two processes and makes the web
  edge restart on every backend change.
- **Build on the server** — slow on 1 vCPU / 1 GB RAM next to the bot, no immutable artefact.
- **Watchtower / pull model** — no CI gate, no health-checked rollback, long-lived registry token.

## Consequences
- Every release is a pair of immutable images; rollback = redeploy an older `sha-…` tag.
- The web check makes the public path (DNS-independent, via `--resolve`) part of the health gate.
- Secrets never leave the server; the pipeline only knows the SSH key and host key.
