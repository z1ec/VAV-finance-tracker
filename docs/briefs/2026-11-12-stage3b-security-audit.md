# STAGE 3b — аудит безопасности: трекер и бот

> Одно задание на два репозитория. Запускается **два раза**: сначала в репозитории трекера,
> потом в репозитории бота. Раздел 2 общий, разделы 3 и 4 — для конкретного репозитория,
> раздел 5 — проверка связки (выполняется во втором запуске).
>
> **Серверы**: `ssh dubai` (root, `81.85.92.119`) — бот и трекер вместе, связь по сети `vav-internal`;
> `ssh ru-tracker` (root) — остановленный старый трекер и **чужой сайт на 443, который трогать нельзя**.

## 0. Перед началом
1. Перенеси файл в `docs/briefs/2026-11-12-stage3b-security-audit.md` текущего репозитория. Ветка `chore/stage3b-security`.
2. Прочитай `CLAUDE.md`, `PLAN`, хвост `DEVLOG`, `ARCHITECTURE`, ADR. Добавь в `PLAN` раздел «Security audit».
3. **Цель** — найти и закрыть реальные риски, а не набрать замечаний. Для каждой находки:
   - серьёзность (Critical / High / Medium / Low);
   - доказательство: файл и строка или команда с выводом;
   - исправление или обоснованное принятие риска.
4. **Серверы — только чтение.** Ничего не меняй ни на одном сервере. Рекомендации по серверам — в `docs/MANUAL_STEPS.ru.md` с точными командами для владельца. На `ru-tracker` особенно: firewall, sshd, чужой сайт на 443 — не трогать.

## 2. Общий чеклист (оба репозитория)
- **Секреты**:
  - история git (`gitleaks detect` по всей истории);
  - `.env*` в `.gitignore`, `.dockerignore`;
  - секреты не печатаются в логах CI;
  - маскировка в логах приложения.
- **Зависимости**: известные уязвимости, нужность каждой зависимости, закреплённые версии в lock-файле.
- **Docker**:
  - non-root, минимальный базовый образ;
  - нет компиляторов и лишних пакетов в runtime;
  - HEALTHCHECK;
  - нет секретов в слоях (`docker history`);
  - `read_only` FS, где возможно.
- **GitHub Actions**:
  - минимальные `permissions` на workflow и job;
  - `pull_request_target` не используется;
  - environment `production`;
  - секреты не уходят в форки;
  - токен GHCR — только через stdin.
- **Деплой-ключ**: доступ пользователя `deploy` — только то, что нужно. Можно ли ограничить ключ в `authorized_keys` (`restrict`, `from=` с IP раннеров — оцени, реально ли; диапазоны GitHub широкие, тогда только рекомендация).
- **Бэкапы**: права файлов, где лежат, сколько хранятся, восстановление проверено.
- **Логи**: нет персональных данных выше DEBUG, нет токенов.

## 3. Трекер (первый запуск)
- **Сессия**:
  - флаги cookie (`HttpOnly`, `Secure` вне localhost, `SameSite`);
  - срок жизни; длина и случайность `SECRET_KEY` (проверка из этапа 1);
  - выход из системы.
- **Перебор паролей**:
  - ограничитель в памяти — работает ли он за Caddy (реальный IP, а не адрес Caddy);
  - что будет при перезапуске;
  - нужен ли общий лимит.
- **Токен бота** (этап 2a):
  - матрица прав;
  - неверный токен ограничивается по попыткам;
  - сравнение за постоянное время;
  - токен принимается только из сети `vav-internal` и без `X-Forwarded-For`;
  - **тот же токен через публичный домен, в том числе с подделанным `X-Forwarded-For`**, получает 403;
  - контейнеры, не подключённые к `vav-internal`, до backend трекера не достают.
- **CSRF**: изменяющие запросы по cookie — `SameSite=Lax` достаточно? Проверь все методы и Content-Type. При необходимости — проверка `Origin`.
- **XSS на фронтенде**:
  - все места `innerHTML` с данными (`common.js`, `expenses.js`, `dashboard.js`, `settings.js`, страница подписок);
  - поле `icon` категории выводится без экранирования — исправь: экранирование и проверка на сервере;
  - комментарии теперь приходят от бота из чеков, то есть **из недоверенного текста**.
- **CSV-инъекция в выгрузке**: значения, начинающиеся с `=`, `+`, `-`, `@`, табуляции или `\r`, экранировать префиксом `'`. Тест.
- **Заголовки безопасности в Caddy**:
  - CSP (с учётом локального Chart.js), `frame-ancestors 'none'`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`;
  - HSTS — осторожно: домен обслуживается на 8443, проверь влияние;
  - проверь, что сайт работает после добавления.
- **Ошибки и раскрытие информации**: `/api/health` ничего лишнего; FastAPI `/docs`, `/openapi.json` наружу не торчат (Caddy проксирует только `/api/*` — проверь фактически).
- **Ввод**:
  - пределы сумм;
  - длина полей;
  - даты;
  - валидация `color` и `icon`;
  - защита от огромных тел запросов (лимит в Caddy).
- **Курсы валют**: `except: pass` при загрузке → логировать; таймауты на внешние запросы.
- **Надёжность деплоя** (не безопасность, но закрываем здесь). На этапе 2b у бота скачивание образа на сервере зависло, потому что у `docker pull` не было таймаута. Это исправлено в PR #8 бота: таймаут, три попытки, лимит задачи деплоя 30 минут. `deploy.sh` и `deploy.yml` трекера сделаны по образцу бота **до** этого исправления. Перенеси тот же фикс и добавь dry-run тест на зависший pull.

  Проверь и автооткат через миграцию. В боте на этапе 3a `deploy.sh` научили перед деплоем делать бэкап базы и восстанавливать его, если новый тег упал после миграции: иначе предыдущий образ не стартует на базе с более новой схемой. Если у трекера та же проблема, перенеси это решение вместе с тестами. Учти урок бота: каталог с данными на сервере закрыт для пользователя `deploy`, поэтому бэкап, проверку и восстановление базы делай внутри контейнера, а не с хоста.

- **Права токена бота: `GET /api/stats/by-category`.** На этапе 3a `/money` бота получал на этот эндпоинт 403: его нет в списке разрешённых для токена (`API_BOT.md`, раздел 4). Исправление 1.4.1 обходит запрет: бот делает по запросу `summary?category_id=…` на каждую из 11 категорий. Добавь `GET /api/stats/by-category` в разрешённые. Это только чтение тех же данных, что бот уже получает через `summary`, так что новых прав у бота не появится. Нужны тест в матрице прав, а также обновлённые `API_BOT.md` и `openapi.json`.

## 4. Бот (второй запуск)
- **Траты по категориям — одним запросом.** Если в первом запуске трекер разрешил токену `GET /api/stats/by-category`:
  - переведи `/money`, «покажи финансы» и виджет «Финансы» с запроса на каждую категорию на один запрос `by-category`;
  - обнови копию контракта через `scripts/update_tracker_contract.py`;
  - `finance-check` проверяет `by-category`.

  Если трекер его не разрешил — оставь как есть.
- **Доступ**:
  - `AccessMiddleware` для всех типов обновлений, **включая `widget_query`** (своё middleware этапа 3a);
  - callback data — проверка владельца сущности в каждом обработчике (дела, напоминания, outbox, подписки, виджеты).
- **Prompt injection через чеки, PDF и голос**:
  - модель ограничена схемой `AgentPlan`;
  - удаление и отмена подписки — только кнопкой;
  - суммы и даты проверяются кодом;
  - в контекст не попадает ничего лишнего.

  Добавь в eval и в тесты 3 кейса с внедрёнными инструкциями: на изображении, в PDF, в подписи к фото. Ожидание — никаких действий, кроме допустимого расхода или уточнения.

  Eval гоняй только с ключом dev-проекта из локального `.env` и только по новым кейсам (`--only`). Ключ с сервера не используй: квота Gemini общая на проект, и прогон оставит прод без ИИ. При `429` запиши в DEVLOG «eval отложен: квота».
- **Экранирование**:
  - HTML-сообщения (`esc`), rich messages, виджеты (`textContent`, экранирование JSON);
  - имена категорий и комментарии из трекера — тоже недоверенные данные.
- **Вложения**:
  - лимит размера и проверка MIME;
  - PDF только передаётся провайдеру, локально не разбирается;
  - временные файлы `data/pending/` удаляются, права `600`.
- **Данные для LLM**: в Gemini уходит только необходимое (контекст дел и категорий). Описать в `SECURITY.md`, что именно уходит внешним провайдерам.
- **Ограничение частоты** входящих сообщений от владельца — защита от случайной петли, расходующей лимиты Gemini.
- **`claude_cli` provider**: путь к бинарю из настроек, `create_subprocess_exec` без shell — подтвердить.
- **SQLite и бэкапы**:
  - права, `export` (JSON) — что в нём, кто может запросить;
  - бэкапы `pre-deploy-*`, которые с этапа 3a делает `deploy.sh`, должны ротироваться, как обычные (`BACKUP_KEEP`). Иначе каждый деплой оставляет полную копию базы. Проверь и при необходимости исправь с тестом;
  - на сервере лежит `/opt/momentum/.env.bak-stage2c` — копия секретов с этапа 2c. Сам не удаляй, добавь команду удаления в `MANUAL_STEPS.ru.md`.
- **Диагностика виджетов** (не безопасность, но закрываем здесь). На этапе 3a `sendWidget` в личный чат вернул `INPUT_MEDIA_WIDGET_NOT_ALLOWED`. Telegram пишет, что виджеты включаются поэтапно, но в личном чате на проде они должны работать. Нужно понять, в чём причина: в Telegram или в наших параметрах.
  - Добавь в `widget-demo` флаг `--minimal`: один статичный виджет без `allow_queries`, без состояния, с HTML в пару строк.
  - Запусти его на проде один раз.
  - Если Telegram его принял — найди, какой параметр полного демо вызывает отказ, исправь и покрой тестом. Флаг `UI_WIDGETS_ENABLED` не трогай.
  - Если тоже `NOT_ALLOWED` — запиши в DEVLOG «виджеты ещё не включены Telegram для бота». В коде ничего не меняй.

## 5. Связка и серверы (второй запуск, только чтение)
- **На `dubai`**: из сети `vav-internal` токен работает; через `https://finance.fomin-vladimir.ru` тот же токен и подделанный `X-Forwarded-For` → 403; сертификат валиден; backend трекера не опубликован наружу (`ss -tlnp` — только 22, 80, 443, 8443).
- **Изоляция стеков**: бот и трекер на одном сервере — что будет, если скомпрометирован один из них (общая сеть, общий Docker-демон, root внутри контейнеров). Оцени и опиши в `SECURITY.md`.
- **SSH**: CI-ключи деплоя (бота и трекера) есть только у пользователя `deploy`, **не у root**; вход root — только по личному ключу владельца.
- **`ru-tracker`**: остановленный стек трекера и бэкапы с данными — напомни в `MANUAL_STEPS.ru.md`, когда и как их удалить.
- **Поверхность серверов** (`ss -tlnup`, `ufw status`/`iptables -S` только чтение, `sshd -T | grep -E 'passwordauthentication|permitrootlogin|pubkeyauthentication'`, `unattended-upgrades`, версии Docker):
  - находки → таблица в `SECURITY.md`;
  - команды для владельца → `MANUAL_STEPS.ru.md`;
  - на российском сервере рекомендации не должны затрагивать соседний сайт и VPN.
- **Ротация секретов**: инструкция в обоих `MANUAL_STEPS` — токен бота, токен Telegram, ключ Gemini, деплой-ключи, `SECRET_KEY` трекера (что разлогинит пользователей).

## Разрешения для режима Auto — отправить ПЕРЕД командой `/goal`
Режим Auto по умолчанию блокирует production-деплой, миграции, изменения секретов и выдачу доступа. Поэтому сначала отправьте агенту это сообщение целиком — оно заранее и **постоянно** разрешает нужные действия на время этой цели. Агент ответит, что понял. Сразу после этого отправляйте `/goal`.

```
Это заранее данные постоянные разрешения для задания, которое я сейчас запущу через /goal. Пока ничего не делай, только подтверди, что понял. Разрешаю на всё время этой цели:
1. Мержить PR этого этапа в `main`, хотя это запускает production-деплой на сервере `dubai` через GitHub Actions. Для трекера это включает изменённые `deploy.sh` и `deploy.yml`: таймаут и повторы `docker pull`, бэкап базы перед деплоем и восстановление этого бэкапа при неудачном деплое после миграции.
2. Создавать issues с меткой `security` через `gh issue create`.
3. Выполнять на серверах `dubai` и `ru-tracker` команды только для чтения (`ss`, `ufw status`, `iptables -S`, `sshd -T`, `docker ps`, `docker inspect`, `cat` конфигов без секретов). Ничего не менять.
4. На `dubai` проверять токен бота для трекера запросами из сети `vav-internal` и через публичный домен — без вывода значения токена.
5. Только в репозитории бота: один раз выполнить на `dubai` `docker exec` в продовый контейнер бота для `python -m momentum widget-demo --minimal`. Эта команда от имени бота отправляет мне в Telegram одно тестовое сообщение-виджет.
Всё остальное, что режим Auto считает опасным, — только с моего отдельного разрешения.
```

Если агент всё равно упрётся в блокировку, откройте `/permissions` → вкладка **Recently denied** → выберите действие → `r` (повторить с ручным подтверждением). Или повторите разрешение сообщением, назвав конкретное действие.
