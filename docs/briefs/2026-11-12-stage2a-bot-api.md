## 2. Вход для бота по токену
- **Настройки** (`config.py` + `.env.example`):
  - `BOT_API_TOKEN_SHA256` — hex SHA-256 токена; сам токен на сервере трекера не хранится;
  - `BOT_API_USERNAME` — пользователь-владелец, от имени которого создаются операции (существующий admin);
  - `BOT_API_ALLOWED_NETWORKS` — CSV подсетей, из которых принимается токен: подсеть Docker-сети `vav-internal` (узнай через `docker network inspect`).
- **Проверка токена**: заголовок `Authorization: Bearer <token>` → SHA-256 → `hmac.compare_digest`. Неверный токен:
  - 401;
  - попытка записывается в тот же ограничитель попыток, что и логин (по IP);
  - токен **никогда** не логируется.
- **Права токена — белый список**, всё остальное с токеном → 403:
  - `GET /api/health`, `GET /api/categories`;
  - `POST /api/expenses`, `PATCH /api/expenses/{id}`, `DELETE /api/expenses/{id}`, `POST /api/expenses/{id}/restore`;
  - `GET /api/stats/summary`, `GET /api/stats/budget`;
  - эндпоинты подписок из раздела 6.

  Права admin у токена действуют только внутри этого списка. Тест-матрица: каждый эндпоинт приложения × {cookie admin, cookie user, токен, без авторизации}.
- **Токен работает только изнутри сервера** — два уровня защиты:
  1. **Caddy** (web-образ) отвечает `403` на любой запрос с заголовком `Authorization` — то есть токен через публичный домен не работает вообще;
  2. **приложение** принимает токен, только если адрес соединения входит в `BOT_API_ALLOWED_NETWORKS` **и** у запроса нет `X-Forwarded-For` (через Caddy этот заголовок всегда есть, значит запрос пришёл снаружи). Пустой список = токен не принимается ни откуда.

  **Проверь опытом**, что Caddy действительно выставляет `X-Forwarded-For`, а клиент не может обойти оба уровня. Запиши вывод в ADR и покрой тестами.
- Вход по cookie для сайта не меняется.

## 3. Защита от двойной записи
- Заголовок `Idempotency-Key` (UUID) на `POST /api/expenses` и на оплату подписки. Хранится в новой nullable уникальной колонке `expenses.client_request_id`.
  - Повтор с тем же ключом и тем же содержимым → `200` и существующая запись, без дубля.
  - Тот же ключ с другим содержимым → `409`.
- Для токена ключ обязателен (без него → 422); для сайта — необязателен.
- Тесты, включая два параллельных запроса с одним ключом.

## 4. Источник и комментарий
- Колонка `expenses.source`: `web | telegram | subscription`, по умолчанию `web`, миграция с заполнением. Токен всегда пишет `telegram`, автосписание подписки — `subscription`.
- Отдаётся в `ExpenseOut`, попадает в CSV. На сайте рядом с операцией — маленький значок (🤖 для telegram, 🔁 для subscription) с подсказкой.
- Магазин хранится в существующем `comment`. Новых полей под магазин нет.

## 5. Часовые пояса (исправление бага)
- **Сейчас**: голые даты `YYYY-MM-DD` и границы месяца считаются в UTC (`stats._parse_dt`, `filters._normalize_date_to`, `/api/stats/budget`). Траты с 00:00 до 01:00 (летом до 02:00) по Будапешту уходят в соседний день или месяц.
- **Нужно**: голые даты — это **локальные дни Europe/Budapest** (`settings.tz`), границы считаются в этом поясе и переводятся в UTC; текущий месяц — тоже по местному времени. Затрагиваются все фильтры по датам, `summary`, `by-category`, `by-month`, `budget`, `export`, список операций.
- `occurred_at` без часового пояса:
  - для токена → 422 «occurred_at must include a timezone offset»;
  - для сайта — как раньше. Фронт шлёт UTC ISO, проверь это тестом.
- **Тесты на границах**: 00:30 по Будапешту 1-го числа, переходы на летнее и зимнее время (29.03.2026, 25.10.2026), выборка «вчера» и «этот месяц».

## 6. Подписки и регулярные платежи
**Модель (миграция)**
- `subscriptions`:
  - `id`, `name`;
  - `amount_type` (`fixed | variable`), `amount` (nullable для variable), `currency` (HUF/EUR/RUB), `category_id`;
  - `period` (`weekly | monthly | yearly`), `interval` (≥1), `anchor_day` (для monthly: 1–31; если в месяце дней меньше — последний день), `next_payment_date` (локальная дата);
  - `remind_days_before` (по умолчанию 3), `is_active`, `comment`;
  - `created_at`, `updated_at`.
- `subscription_charges`:
  - `id`, `subscription_id`, `due_date`, `status` (`pending | paid | skipped`), `amount`, `currency`, `expense_id` (nullable), `created_at`, `updated_at`;
  - `UNIQUE(subscription_id, due_date)`.

**Планировщик** (существующий APScheduler)
- **Когда**: ежедневно в 06:00 Europe/Budapest и один раз при старте — догоняет пропущенное.
- **Для каждой активной подписки** с `next_payment_date <= сегодня` (по каждой пропущенной дате):
  - создаётся charge (идемпотентно);
  - `fixed` → создаётся расход: `source=subscription`, `occurred_at` = дата списания 12:00 по Будапешту, категория подписки, комментарий `Подписка: <name>`; статус `paid`;
  - `variable` → статус `pending`, бот спросит сумму;
  - `next_payment_date` сдвигается по периоду с учётом `anchor_day`.
- **Повторный запуск** не создаёт дублей (тест).

**API** (cookie admin и токен; cookie user — только чтение)
- `GET /api/subscriptions?active=true`, `POST /api/subscriptions`, `PATCH /api/subscriptions/{id}`, `DELETE /api/subscriptions/{id}` (деактивация, не удаление).
- `GET /api/subscriptions/upcoming?days=7` — будущие списания в окне `max(days, remind_days_before)` плюс все `pending` charges.
- `POST /api/subscriptions/charges/{id}/pay` `{amount, currency?, occurred_at?}` + `Idempotency-Key` → создаёт расход, `paid`.
- `POST /api/subscriptions/charges/{id}/skip`.
- `GET /api/subscriptions/summary` — сумма активных подписок в HUF в месяц: weekly ×52/12, yearly /12, по последним курсам. Плавающие считаются по последнему оплаченному charge, а если его нет — не входят в сумму (и это видно в ответе).

**Сайт** (существующий дизайн `style.css`, `escapeHtml` для всего пользовательского текста)
- Новая вкладка «Подписки»:
  - список: название, сумма, период, дата следующего списания, категория, статус;
  - форма добавления и редактирования;
  - блок «Ждут суммы» для `pending` с кнопками «Внести сумму» и «Пропустить»;
  - итог «в месяц».
- На дашборде — блок «Ближайшие списания (7 дней)» и сумма подписок в месяц.
- Права как у операций: user видит, admin меняет.

**Тесты дат**: 31-е число в коротких месяцах, 29 февраля, yearly, weekly с `interval=2`, догон пропущенных дат, деактивация.

## 8. Деплой и настройка связки
1. PR → CI → merge → Deploy `success`. До деплоя миграции проверяются на **копии прод-БД на сервере**: временный контейнер нового образа с копией в `/tmp`, `alembic upgrade head`, `PRAGMA integrity_check`, сверка числа строк, затем удаление копии. Прод-данные на рабочую машину не копировать.
2. **Токен — без вывода значения**:
   - сгенерируй случайный токен (32 байта) **на сервере**;
   - **SHA-256** запиши в `/opt/finance-tracker/.env`: `BOT_API_TOKEN_SHA256`, `BOT_API_USERNAME`, `BOT_API_ALLOWED_NETWORKS`;
   - **сам токен** запиши в `/opt/momentum/.env`: `FINANCE_API_URL=http://finance-backend:8000`, `FINANCE_API_TOKEN=…`;
   - всё в одной команде на сервере, чтобы значение не попало ни в вывод, ни в историю shell; права файлов `600`, владельцы прежние.
   - Перезапусти только стек трекера: через `deploy/deploy.sh` с текущим тегом или `IMAGE_TAG=$(cat .last_successful_tag) docker compose … up -d` (прод-compose требует `IMAGE_TAG`). Бот этих переменных пока не читает, его не перезапускай.
3. **Проверка связки** без изменения данных — временным контейнером в сети `vav-internal` (`docker run --rm --network vav-internal curlimages/curl …`), токен подставляется из `/opt/momentum/.env` внутри команды:
   - с токеном: `GET http://finance-backend:8000/api/categories` → 200, `/api/stats/budget` → 200, `/api/subscriptions/upcoming` → 200;
   - без токена → 401;
   - с токеном на `POST /api/rates/refresh` → 403;
   - **тот же токен через публичный домен** (`https://finance.fomin-vladimir.ru/api/categories` с рабочей машины) → 403;
   - бот по-прежнему `healthy`.
4. **Идемпотентность и создание расходов** проверяй e2e-тестом против временного контейнера с тестовой БД, а не на проде.
